5. Correct the offline acceptance invariant

Replace any absolute rule such as:

"Completed offline sales are accepted once"

with a safer invariant.

The plan must distinguish:

- client-visible locally completed operation
- server acceptance
- server quarantine/rejection

A retried operation with the same valid idempotency key must never create duplicate financial or inventory effects.

The server may quarantine or reject an offline operation if it is:

- tampered
- malformed
- unauthorized
- from a revoked/expired device
- outside allowed policy
- inconsistent with required integrity checks

The system must preserve an auditable recovery path and must not silently lose the cashier-visible transaction.

Define this concept at architecture level only; do not prematurely design a complex protocol.

6. Resolve negative-stock / offline oversell architecture at planning level

Document a Medusa-compatible strategy.

Requirements:

- Medusa remains the inventory source of truth
- do not introduce a second authoritative inventory balance
- do not use unsafe direct database writes into Medusa internals
- server reconciliation must go through supported service/workflow boundaries
- legitimate offline oversells must produce an explicit exception/reconciliation state
- define whether V1 permits negative available stock, records an inventory discrepancy, or uses another supported mechanism
- if exact Medusa behavior requires later technical validation, mark it as a blocking implementation research task before Offline POS coding

The ADR must state the invariant even if the exact API/workflow is validated later.
